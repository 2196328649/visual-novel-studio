# 开场音乐与菜单持续动画

日期：2026-11-10。状态：本分支源码与原生专项已完成；开场最终覆盖 19 场景／22 用例／385 断言，另有 Spine 14 用例／66 断言和视频 10 用例／47 断言回归通过。首轮一次性视频采样契约失败已保留证据并完成定向复验，计数与清理见末节。整批其他工作及最终脚本类型检查由主代理统一收口。

本轮对应用户指出的两个问题：没有音乐节点的开场仍提前播放标题曲；开场进入标题的连线过渡中，标题上的循环动画停在一帧。

## 音乐进入边界

Ren'Py SDK 的 `00start.rpy` 先播放 `config.main_menu_music`，再进入 `_main_menu` 上下文并调用 `before_main_menu`。项目开场恰好在这个 hook 内执行，因此之前标题曲早于开场启动，并非开场图中存在隐藏的音乐节点。

生成配置现在将 `config.main_menu_music` 留空，曲目与淡入时长分别保存在 `vn_main_menu_music`、`vn_main_menu_music_fadein`。项目自身的 `main_menu` 标签显示真实目标页面后，先接管标题曲，再执行连线过渡。这样开场播放期间不会自动出现标题音乐；开始转入标题时响起标题曲。接管使用 `if_changed=True` 保持相同曲目的续播与既有淡入设置。未设置标题曲时，进入标题会停止开场留在 music 通道的音乐。

只有确定本次要执行开场步骤时，才在首步骤之前停止一次旧 music 通道。每一步之间不插入停音，作者在开场里主动播放的音乐可以连续经过页面、视频等步骤。没有开场步骤、只配置启动到标题的过渡，或本次重复策略跳过开场时，不增加这一停音。新游戏、读档及开场重复策略原有语义保留。

标题宿主在开发热重载后可能恢复到设置页，因此接管不依赖 screen 名称必须等于 `main_menu`。普通设置页与标题之间的直接 screen 导航继续保持当前音乐，不重新执行开场。

## 过渡中的媒体

页面显示事件、自动关闭计时与媒体播放不再共用一个暂停条件：

| 内容 | 过渡期间 |
| --- | --- |
| 自动循环的 Spine、循环视频控件 | 从目标开始绘制时持续播放，成为实际目标画面的一部分 |
| 一次播放的 Spine、视频控件 | 保留开头，过渡结束后再完整播放 |
| 顶层视频模块、舞台时间轴中的短媒体 | 保留原有入场暂停与释放规则 |
| 页面创建／显示事件、页面自动关闭 | 仍等过渡结束后才开始 |
| OnShow 蓝图启动的属性动画 | 随 OnShow 在过渡后启动，不提前执行作者蓝图 |

循环视频由同一媒体通道播放画面与内嵌音轨；两类媒体保留页面隐藏、裁切、关闭和显式暂停规则，Spine 的播放速度控制继续生效。本轮无声视频 fixture 未直接验证内嵌音轨同步。当前真实工程的 `ai_title_animation` 使用 `autoplay=true`、`loop=true` 的 Spine；它不依赖 OnShow，因此直接适用持续视觉规则。真实工程仅作只读核对，未修改素材或工程设置。

持续媒体可能在过渡中发现解码／素材错误。视频与 Spine 的 `ended`／`completed`／`failed` 事件以可保存的 `eventPending` 标记保留，到页面实际进入后再交付。每个事件在自己的回调前消费一次；其他尚未交付的事件仍能随存档保存。关闭页面、重开、换素材或重播会清理或替换对应记录，旧页事件不会交给新页。旧 v1 记录没有这个新增字段时按没有待交付事件读取。

`didShow` 表示页面入口事件已经开始，不表示入口蓝图中所有带等待的代码已经结束；原有允许事件交错的生命周期规则保留。图片加载成功／失败回调不在本次媒体暂停修改范围内，不能把此修复概括为所有资源回调统一延后。

### 待交付事件的存档验收边界

既有视频与 Spine 游戏用例覆盖暂停后保存／读档、关页回退、返回标题后重新开始，以及完成事件交付后读档不重复派发；它们不直接覆盖 `eventPending=true` 的存档。标题循环坏媒体专项验证真实过渡内失败、页面进入前不派发、进入后交付一次。

标题开场与菜单本身在 SDK `call_in_new_context("_main_menu")` 的非回退子上下文运行，正常存档只恢复基础游戏上下文。`FileSave` 在标题禁用；直接调用 `renpy.save` 能写文件，也不能据此恢复原标题页面实例。因此不把标题专项描述成支持标题菜单存档。

本轮另补两项隔离场景 `pending_video_load`／`pending_spine_load`：先通过真实开始游戏按钮进入基础游戏上下文，由新游戏前的图片模块过渡到自定义页面，在坏循环媒体自然失败、`eventPending=true` 且页面 `didShow=false` 时保存并读档，再检查页面进入后交付一次及关闭释放。随后保存已经交付的状态，关闭页面再读回，要求不重复解码、派发或创建页面。两场景各 26 条原生断言已通过。此处验证的是可存档游戏页面的媒体事件生命周期，原有标题视觉与事件时序场景保留。

两项新增用例完成独立静态审查后运行，原有 17 场景／20 用例／333 断言保持；合计最终覆盖 19 场景／22 用例／385 断言。既有 `verify-ui-spine-runtime.ts`（14 用例／66 断言）与 `verify-ui-video-runtime.ts`（10 用例／47 断言）也已通过。两份旧脚本只补 `VNS_ARTIFACT_ROOT` 输出根支持，未设置时保持原目录；运行时显式使用仓库 `resources/runtime` SDK。

首轮失败来自 `gft_ui_once_video_held` 对 SDK 返回值的假设。真实记录中 60 个已解码首帧样本覆盖 2.766 秒，均处于暂停和过渡保持状态、保存位置为 0、同一来源序号和素材、没有提前事件；实际像素沿红色叠化到片头品红，没有第二段青色。SDK `renpy/audio/music.py` 的 `get_pos()` 会将位置 0 返回为 `None`，旧探针用原生位置非空筛选样本，导致合法首帧被全部丢弃。

仅修正此探针：全部已解码帧仍必须暂停并保持、来源与素材一致、保存位置为 0；两处像素全程属于红色到品红的路径且不能出现青色。原生位置可用时仍检查最大值不超过 0.15 秒、变化不超过 0.06 秒，没有把空值改成 0。原生 18 条断言及过渡后的完整播放、两色持续时长、一次完成要求均保留，并由另一代理独立回读。复验过渡为 2.859 秒，首帧 60 个样本跨度 2.765 秒；过渡结束后 1.297 秒完成原长 1.2 秒的视频，仅派发一次结束。原生验收期间没有修改产品源码。
