## 1. 结论

现在的复杂感有四个具体来源：

1. **参数可信度不足。** 有些字段缺少入口，有些能填却没有效果，还有些默认值与真实取值不一致。先解决这些问题，用户才能相信面板。
2. **同一任务被拆散。** 按钮某个状态的图片、背景、文字色、亮度分在不同位置；滑条外观挤在“内容与素材”里，外面又有另一组“外观与状态”。
3. **编辑范围混在一起。** 整个列表、重复条目、条目里的缩略图或文字、整个素材库，有时都在一条纵向参数流里。
4. **连续操作成本偏高。** 切到另一个同类控件会回顶部并关闭正在编辑的分组；窄面板里长标签仍固定两列；继承值、单独设置的值和运行时绑定值区分不够清楚。

建议先修正功能与显示，再保留折叠分组做任务化整理。不要一次性重写所有控件，也不要仅靠“全部默认收起”掩盖入口问题。

## 4. 源码发现、尚需专项操作验证的风险

| 风险 | 依据与影响 | 建议 |
| --- | --- | --- |
| 切换绑定类型残留不兼容的范围 | 数值切换为字符串或开关时，`controlRange` 没有一并处理；项目校验有不兼容报错路径。见 `PlayerPreferences.tsx:36`、`validate.ts:355` | 绑定切换做一次完整更新，明确哪些数值配置失去适用性，并支持撤销 |
| 历史列表混入普通网格字段 | 固定纵向历史列表与普通集合共用行列、条目宽高编辑；姓名宽度与最小行高仅在分列模式使用。见 `UiAppearance.tsx:117,171`、`UiHistoryPreview.tsx:39`、`ui-widgets.ts:375` | 历史专用布局面板：排列方式、对白区、姓名区、语音按钮、滚动条，按当前模式显示 |
| 历史姓名字号预览与游戏可能不同 | 预览在上下、分列两种模式都使用姓名字号；游戏上下模式使用通用字号，分列才使用单独设置。见 `UiHistoryPreview.tsx:45`、`ui-widgets.ts:404,411` | 确定统一语义后补两模式实际游戏用例 |
| 图片、视频、骨骼的通用背景与边框可能预览／游戏不一致 | 编辑器通用容器绘制，与游戏按属性适用种类限制有差异。见 `UiComponentVisual.tsx:13`、`screens.ts:110`、`ui-properties.ts:34` | 逐类确认支持范围；字段、预览和运行时共用能力定义 |
| 状态图片的继承提示过于简化 | 面板统一写“沿用普通图片”，实际按住／选中的解析链可能经过悬停图。见 `UiAppearance.tsx:102`、`ui.ts:35` | 显示实际来源，不修改原解析规则 |
| 快捷键编辑器与预览键集合不同 | 面板列出 A–Z、数字、F1–F12；页面预览依赖另一套蓝图键目录。见 `UiAppearance.tsx:86`、`blueprint.ts:117`、`ui-logic-preview.ts:85` | 使用统一键定义并补键盘预览验证；本轮没有逐键实测 |
| 字号被控件高度隐式限制 | 共用与运行时代码包含 `max(12, min(填写字号, 高度×0.7))`。见 `ui.ts:63`、`ui-runtime.ts:387` | 先提示有效字号及限制原因；是否新增“固定字号／自动适配”需要单独讨论，会改变既有显示 |
| 创建参数联动会不断增加独立蓝图和轮询 | `createUiParameterBinding` 每次新建一个图，含 0.05 秒重复定时器；入口缺少明确的当前绑定、替换和解除。见 `UiParameterBindings.tsx:28`、`ui-logic.ts:112` | 先能看见、定位和替换自动生成的绑定；不要误删用户手写蓝图。事件驱动调度需另做行为与性能验证，本轮未测出性能回归 |
| 条件开关启用后创建空条件 | 空的 all 条件实际恒真；选中条件还能覆盖按钮本身的自动选中规则 | 显示自然语言结果，如“始终显示”“跟随开关状态”，添加第一条规则时再进入编辑；保留高级表达式 |
| 所有内部部件启用自定义位置时套同一矩形 | `UiRectFields` 使用 5%、5%、90%、40%，不等于缩略图／摘要／滚动条各自当前区域。见 `UiAppearance.tsx:212` | 用当前实际矩形作为初始值，启用自定义后保持画面不跳动 |

以上仍是待修复风险，不应写成“本轮游戏验收失败”或“全部控件已经证明失效”。

## 6. 推荐的共同结构

### 顶部：对象与编辑范围

显示“控件属性 → 返回按钮”，必要时注明页面、继承来源；多选时明确写出“属性仅编辑最后选中的对象”，批量布局工具则注明影响全部选中对象。当前已经有末选对象提示，优化目标是更清楚，不能说现有多选完全损坏。

属性搜索属于增强项。支持中文名称和常用同义词，命中后打开对应分组并定位字段；清除搜索后恢复之前的分组，不改变任何属性。

### 内容／绑定

只放决定“它显示什么、读写什么”的设置：固定文本、素材、参数来源、选项内容、列表数据入口。滑条用“音乐音量 · 0～100% · 跟随来源”一行表达有效范围；自定义范围展开后仍一次应用上下限和步长，不改成每个输入立即写入非法中间状态。

百分比只是音乐音量这样的明确单位示例。普通游戏参数保持自己的数值单位；界面展示换算不改变存储单位和运行规则。

### 位置与大小

常用 X/Y/宽/高保持紧凑，始终标注百分比、画面像素以及相对页面还是父对象。锚点、轴心、旋转、缩放收在“更多布局”。只有容器任务需要时才展示子项排列、内边距和滚动；已保存但当前不适用的配置应有摘要和定位入口，不能悄悄抹去。

### 外观

按钮改为先选状态，再在同一处编辑该状态的图片、背景、文字色与亮度，预览同步到该状态。字体、字号、对齐和描边阴影放在相邻区域。字体选择继续支持项目素材搜索／浏览／导入，现有能力可直接复用，不应误称目前只有几个固定字体。

保留页面字体继承。字体本身通常是所有状态共用，字段明确注明；切换按钮状态不应制造不必要的五份字体覆盖。透明色、未设置、显式设置同值要可区分。

### 交互

简单任务使用“点击后 → 返回上一页”“显示 → 满足条件时”“可操作 → 始终可操作”等直接表达。复杂事件折叠展示真实顺序，可跳到已有蓝图。点击摘要共用实际处理器分析，避免 UI 自己再次拼一套简化逻辑。

只读“蓝图属性能力”放到帮助／参考入口；它有用途，但不需要占据修改外观的主要路径。

### 所有分组共同遵守

- 每个值能回答：当前实际是多少、沿用哪里、是否被单独设置、是否由参数／事件控制。
- 单项恢复和分组恢复按范围操作；整体恢复明确说明会恢复哪些内容。
- 阴影、描边、九宫格、自定义范围等先显示状态和摘要，启用或展开后再显示细节。
- 在同类控件之间继续保留正在修改的分组／按钮状态；不同类型切换按任务映射，不机械保留一个可能落在无关内容上的滚动像素。
- 所有重排保持撤销、保存重开、继承和现有数据兼容。

## 7. 特殊控件的编辑方式

### 存档、历史、收藏：可选择的条目模板

推荐层级是“整个列表 → 一个条目模板 → 条目里的部件”。点击预览里的缩略图、章节或摘要，右侧就只显示该部件的参数，顶部明确“影响此控件的全部存档条目”。返回“整个列表”再调整列数、行数、间距与分页。

这不是创建几十个独立控件，也不改变存档数据结构。先复用已有内部区域；开启自定义区域时从当前布局计算起点，避免画面瞬间跳位。

### 图鉴、音乐：内容管理从属性里分离

右侧保留“内容：已选择 N 项／使用全部素材”和“管理内容”入口；添加、移除、排序、筛选在更宽的列表中完成。属性面板主要处理网格、条目和播放交互，避免把素材库全堆在窄栏中。

### 玩家剧情图：继续已有方向

内容、节点样式、布局与连线、玩家操作四组已经落地，本轮不建议推倒重做。下一步明确三种范围：

- 整张图：基础字体、布局、连线与玩家操作。
- 当前节点：实际文字、分段和使用哪个“节点外观预设”。
- 预设库：编辑某个预设时标明影响多少节点，并能定位使用者。

当前节点的每段实际文字应与对应字体、字号放在一起。切换节点不能暗中切成修改全局预设；刚完成的柔边黑底和来源／覆盖规则必须保留。

## 9. 代码整理建议

不建议按“文件长”直接拆成大量小文件。当前更值得合并的是重复的语义：

1. **统一字段能力与有效值解析。** 编辑器用一套 kind 判断，预览和运行时又用另一套，已经产生皮肤、边框和默认色差异。基于现有 `ui-properties`、`ui-control-properties` 和主题解析补齐能力元数据，不另造第二套完整注册表。
2. **让属性分组有明确写入范围。** `style = undefined` 这种整块恢复与按任务分组冲突。给单项、外观、素材适配等定义可复用的恢复操作，保留一次操作一个撤销记录。
3. **将输入模式解析与渲染分开。** `preference`／`preferenceChoice` 可以随绑定变成滑条、开关、输入框或选项控件，名称与显示字段应来自解析结果，不继续叠加零散分支。
4. **特殊列表各自提供内容编辑模块。** `UiAppearanceFields` 同时承担外观、内容、交互，容易漏入口和展示错误字段。保留共享基础字段，把历史、存档、图鉴等业务组按任务拆出，逐个替换。
5. **复用真实行为分析。** 点击摘要用 `uiClickHandlers`；参数绑定显示当前来源及已有自动生成图，避免每次创建新图都让后续难以管理。

折叠记忆、按需挂载昂贵预览、局部派生值缓存可以作为性能方向；需要用同一大工程测量后再决定。本轮没有性能采样，不能宣称这些就是此前所有卡顿的原因，也不能承诺改完必然不卡。

## 10. 建议实施顺序与验收

**第一批：参数可信度。** 补绑定／输入入口；修失效绑定；修真实默认值；纠正恢复范围、事件摘要、历史滚动条、图鉴行数和存档文字预览；核实圆角、皮肤和通用边框的实际支持。无效字段先撤下或明确不适用；新增渲染能力要单独确认工作量，不把它当成纯排版修复。

**第二批：常用编辑体验。** 同类型切换保持任务位置；按钮状态集中编辑；滑条内容与外观拆开；数值紧凑排列；字段按适用条件出现；把能力说明移入帮助。属性搜索可以随这一批做，多选批量属性编辑排在核心体验之后。

**第三批：特殊控件。** 存档／历史／收藏的条目与内部部件编辑，图鉴／音乐内容管理，以及剧情图当前节点、整图和预设库的范围提示。

需要单独商量的行为变化：固定字号与自动适配的切换规则；参数绑定是否由轮询改为事件驱动；新增图鉴滚动模式；跨对象批量写入的继承和冲突规则。重玩、解锁、文字计时及已有原生菜单语义不随这次面板整理改变。

实现全部完成后再按用户要求统一编译、验证、验收：

- 值与效果：未设置、显式设置、恢复默认分别验证，至少覆盖透明背景、状态色、圆角／皮肤的支持范围、图鉴行数、存档显示开关。影响运行时的字段补实际游戏验证。
- 安全编辑范围：失效绑定不假选；绑定类型转换无残留冲突；恢复字体不改变图片适配、其他状态或绑定；撤销和保存重开验证一次。
- 连续任务：连续给两个按钮改同一状态／字体不重复寻找分组；约 220／280／360px 面板宽度下字段可读可操作。
- 特殊控件：所有 23 类代表样例可达；每类关键内容可编辑；选择条目部件后编辑范围准确；启用自定义位置保持现有画面。
- 实现后才制定有意义的针对性自动用例，避免只断言输入框成功填写而没有验证实际行为。
