# 控件组件化的补充设计：身份、覆盖、输入与双端契约

日期：2026-11-09。**状态：只读研究与建议，本文所述新增机制均未实施。**

用户本轮先实施流程连线过渡；控件组件化继续研究。本文件不改变组件格式、运行行为、现有模板或用户工程，也不构成已授权实施全部提案的清单。组件研究子任务只新增本文档，没有为这部分运行编译、测试或产品验收；已实施的连线过渡及其统一验证另见 [功能与验收记录](flow-transitions-2026-11-09.md)。

本文件接续已有“通用属性在上、实际功能在下、功能目录与复合控件模板”的分析，补充六项会决定后续是否易用、可靠和可扩展的规则。已有属性右键三模式、框选、通用／内部部件分层继续复用，不再作为待实施功能。当前状态见 [属性控制记录](ui-property-control-2026-11-09.md)、[属性面板分层记录](ui-inspector-hierarchy-2026-11-08.md) 和 [框选记录](ui-marquee-2026-11-09.md)。

## 建议优先级

“先定规则”指在引入新数据格式或可复用控件前形成清楚契约，不要求先把所有功能实现。P0 为会影响保存和引用的基础规则，P1 为下一轮组件化值得实现的直接收益，P2 为边界稳定后再扩展。

| 新增建议 | 应提前确定 | 优先产品收益 | 首版应后置 |
| --- | --- | --- | --- |
| 1. 区分对象、功能组件和字段分组，建立稳定寻址 | P0：身份、引用、重复项键、复制规则 | P1：模板公开字段可以直接定位到内部对象 | 任意嵌套运行时组件、任意同类组件堆叠 |
| 2. 模板覆盖采用差量与三方比较 | P0：继承／清空／覆盖、移除冲突、更新目标 | P1：本地只改标题，其余设置继续跟随模板 | 多重模板继承、任意脚本合并、无提示全项目级联更新 |
| 3. 布局与输入各有明确责任者 | P0：位置谁决定、点击交给谁、何时取消焦点 | P1：图文按钮、滚动列表和弹窗组合后仍可预测 | 完整事件传播编辑器、无限约束布局 |
| 4. 样式来源可追踪，长文字处理成为显式设置 | P0：状态回退、文本来源、设计值与有效值区别 | P1：尺寸改变或文本变长时不会悄悄改变作者意图 | 全套主题选择器、复杂语言规则编辑器、无限状态组合 |
| 5. 多选按共同能力批量编辑，响应式先覆盖常见约束 | P0：混合值、混合来源、原子提交及父子范围 | P1：统一多个标题的字体／颜色等高频工作 | 任意多选结构变更、全套断点布局系统 |
| 6. 扩展需要版本化双端契约 | P0：未知数据保留、版本迁移、能力一致性 | P1：内置组件也按同一规则注册和交付 | 动态代码插件市场、运行中热换插件 |

## 1. 功能卡片不必都变成运行时组件，身份要先稳定

**新建议：用“需要独立空间、独立生命期、独立引用”决定粒度，不按面板折叠标题拆数据。**

现在对象用 `id + parentId` 形成子树；动画用 `componentId + property` 指向对象属性。`duplicateUiSubtree` 会生成新对象 ID 并重映射父级，但函数本身不复制蓝图、动画或重写其中的组件目标。这符合当前“复制对象”的边界，不能直接升级为“复制完整复合控件”而保留原假设。

代码依据：[对象子树与复制](../src/core/ui-hierarchy.ts#L57)、[复制实现](../src/core/ui-hierarchy.ts#L158)、[子对象复制入口](../src/renderer/UiChildObjects.tsx#L76)、[动画引用](../src/core/model.ts#L635)。

建议采用以下界限：

| 类型 | 判断方式 | 例子 |
| --- | --- | --- |
| 对象／子对象 | 有自己的位置、尺寸、排序、可选择范围 | 按钮标题、图标、角标、滑块 |
| 功能组件 | 有独立的数据／行为契约，需要启停、依赖或公开引用 | 按钮输入、重复列表、视频播放、自动排列 |
| 字段分组／可选能力 | 是已有功能的一组配置，无需独立运行身份 | 文字描边参数、图片九宫格边距、按钮两项音效 |

例如“文字阴影”可以显示为可启停卡片，但首版不必为每个阴影建立运行时组件实例、事件和存档记录。反过来，滑块如果能独立摆放和替换，它是子对象，不应只是“滑条外观组件”里无法寻址的几组坐标。组件粒度过细会把当前的字段复杂度变成组件复杂度。

每个对象首版应只允许一个主布局驱动和一个主输入行为。需要多个独立视觉元素时，优先使用子对象；需要多种行为时允许有序的事件动作或有明确实例身份的行为组件。禁止通过面板列表顺序无声地决定哪个组件最后覆盖另一个组件。

寻址需分清四层：

1. **定义身份**：对象 ID、功能组件实例 ID、属性 ID。名称、树路径、数组下标都不是稳定身份。
2. **模板实例身份**：模板内部 ID 映射到具体实例，不把编辑模板时的对象 ID 当成所有实例的同一对象。
3. **重复项身份**：条目模板内部对象还需一个稳定 `itemKey`，例如存档槽 ID；列表排序、分页和虚拟化不能让“第 2 行”突然指向另一条数据。
4. **运行会话身份**：页面 token／实例代次。页面关闭再打开后，旧回调、媒体事件、焦点命令不得作用到新实例；token 是运行态，不作为作者引用保存。

内部可使用结构化引用，用户看到“声音设置行 → 音量滑块 → 当前值”。模板对外尽量公开语义端口，例如“标题”“图标”“当前值”“确认事件”，外部蓝图无需知道内部第几层。

**复制契约应在可复用模板前确定：**实例内引用重映射到新实例；共享参数、素材和共用蓝图继续引用共享定义；不确定是否为内部引用的字符串不能全局替换。功能注册需要同时登记可扫描、可重映射的引用字段。可以分别提供“复制对象外观”与“复制对象及专属行为”，但操作名称必须说明范围。

首版不用开放任意重复组件和任意运行时对象生成；先让一个图文按钮和一个设置行在复制、保存重开、动画定位时身份正确。

## 2. 模板逐字段覆盖需要三方比较，不能只做深合并

当前界面方案按同 ID 整控件替换，第一次编辑完整克隆。恢复整控件已经检查对下游方案父子结构的影响，因此未来逐字段恢复也必须维持这一完整性要求。

代码依据：[整控件解析](../src/core/model.ts#L754)、[首次编辑克隆](../src/core/model.ts#L865)、[恢复时检查派生层级](../src/core/ui-hierarchy-edit.ts#L14)。

**新建议：模板值至少区分“继承”“显式设置”“显式清空”，结构变更和字段变更分别存储。**

- 没有本地记录表示继承，不能在读取时把解析出的默认值写成本地覆盖。
- 显式设置包括 `0`、`false`、空文字，不能用真假值判断是否存在。
- 显式清空表示有意不使用上级素材、音效或内容；不能把清空误当继续继承。
- “还原覆盖”是删除本地操作，恢复上级值；不是写入一个恰好等于当前上级的数值。
- 一些操作须作为完整单元，例如 `{mode, parameterId}`，不能从两个版本各合并半条参数关联。范围、输入类型与来源可逐字段编辑，但应用合并结果前必须整体验证。
- 重复元素按稳定 ID 合并。动画帧、子对象或状态条目不能按数组位置合并。

这里不能统一把 `null` 定义为删除：当前音效配置已经使用 `undefined` 表示沿用、`null` 表示静音。因此新的差量记录需要显式操作类型，而非复用某个业务值作为通用删除标记。

更新模板时应比较“用户开始覆盖时的上级版本、当前上级版本、本地修改”：

| 场景 | 建议结果 |
| --- | --- |
| 本地没改字号，上级把 24 改成 28 | 更新到 28 |
| 本地把标题改为“继续”，上级只改字号 | 保留标题，更新字号 |
| 本地和上级都改同一字号 | 保留本地值，显示上级变化；允许明确还原 |
| 上级删掉子图标，本地改过该图标颜色 | 标记“内部对象已移除”，保留可恢复的覆盖记录；不把颜色写到同名新对象 |
| 上级把数值输入改为文本输入，本地仍关联数值参数 | 标记契约冲突，不能自动转换、清空参数或让关联失效而不说明 |

建议首个模板版本记录所依赖的模板修订。更新可预览影响并一次应用；避免刚开始就让任何模板编辑实时级联到整份工程。后续只有不涉及本地覆盖和结构冲突的兼容更新，才考虑自动跟随。

模板变体应是单继承链，不引入多继承。同一实例所在的界面方案和所用控件模板是两个维度：界面方案决定哪些对象／实例存在及当前实例配置，模板链解析实例内部内容。不要将两套继承的所有字段压成一条不透明的全局覆盖链。

“应用到模板”也需明确目标：基础模板、当前变体、实例本地三个目的地不等价。操作前展示实际影响的实例范围，不能默认写到最顶层基础模板。

首版组件卡片无需顺带实现完整模板合并器。应先定差量与身份格式，模板首批只允许有限的公开字段覆盖，再扩大到结构覆盖。

## 3. 组合后仍可预测：布局与输入各有明确责任者

### 布局不是多个组件依次改坐标

当前布局按项目虚拟分辨率和父级比例计算，横／竖排列生成子项槽位，X/Y 继续是附加偏移。背景子对象以父外框为基准，不参加前景排列和滚动。布局计算已有测量、放置、裁切两个阶段；换父级遇到参数受控几何或不可表示的斜切会拒绝，避免无声改画面。

代码依据：[布局计算](../src/core/ui-layout.ts#L95)、[背景与前景的排列规则](../src/core/ui-layout.ts#L109)、[换父级保护](../src/core/ui-hierarchy.ts#L126)。

**新建议：将“布局决定的矩形”“作者附加偏移”“演出变换”分开命名并约束写入。**

父容器决定槽位，子对象决定其允许的尺寸方式，局部偏移用于微调。若将来增加入场动画，优先对演出偏移／透明度动画，避免每一帧重新改变整个横排布局。已有 X/Y 动画和附加偏移语义保留，不能在迁移中悄悄改成另一空间。

新增“根据内容调整”时要禁止自相矛盾：父宽跟随子内容，而子宽又是父宽的 100%，不能靠反复测量直到碰巧稳定。应明确要求一端有可确定的约束。布局依赖还需标记“影响测量／只影响绘制／只影响输入”，改颜色不应重算整棵树；字体、文本或可见性影响布局时只使相关子树失效。

### 可点击子对象不能让父按钮再执行一次

游戏当前已有页面 token、输入穿透、模态遮挡、隐藏／禁用／裁切检查，以及按压／焦点取消。预览同样带页面实例身份，失效焦点会被撤销。这些是可复用控件必须继续遵守的基础，不应让每个自定义组件自行绕开。

代码依据：[运行时可操作性](../src/runtime/ui-runtime.ts#L447)、[焦点恢复与取消](../src/runtime/ui-runtime.ts#L580)、[预览焦点检查](../src/core/ui-logic-preview.ts#L714)、[滚动和裁切事件](../src/runtime/ui-layout-runtime.ts#L32)。

建议先确定最小交互契约：

- 纯图片、文字、装饰默认不拦截玩家输入；它们可以随父按钮显示状态变化。
- 命中子按钮时执行子按钮；默认不再自动执行父按钮的点击主操作。状态继承不代表事件继承。
- 需要父级观察时，显式注册观察／传播行为，事件携带原始目标、当前处理者和重复项上下文；不用浏览器原生冒泡来替代游戏语义。
- 一个指针手势有唯一捕获者。按下后弹出模态界面、控件被停用或移除，原手势取消，不在松手时补发旧点击。
- 可聚焦的是实际输入功能，不是所有视觉对象。焦点顺序、方向导航和鼠标绘制顺序分别表达。
- 用户按 Enter 或主动离开输入框可触发提交；被隐藏、销毁或模态层覆盖属于取消／暂存。输入法确认候选不应误当提交。
- 关闭弹窗后仅在原页面代次和原目标仍有效时恢复焦点。重新打开的同名页面是新会话。
- 嵌套滚动由最内层能实际滚动的容器消费；到边界后如何交给父级固定为一致规则，一次输入不能同时滚动多层。

第一个图文按钮模板就应覆盖“点击文字也点中按钮、点击内部独立操作不触发父操作、键盘激活只执行一次”三种交互。首版不需要完整的捕获／目标／冒泡编辑器，也不必先提供任意手势脚本。

## 4. 把样式来源和长文字处理做成可解释的机制

现在图片状态有 `pressed → hover → idle` 等回退；文字颜色与背景颜色有各自的回退。普通文字、按钮等还受 `uiComponentFontSize` 的 12px 下限和控件高度 70% 上限影响。预览和游戏都复用这项规则，所以“设置字号”和“实际显示字号”不同不一定是单端缺陷。

代码依据：[颜色与图片回退](../src/core/ui.ts#L12)、[当前字号规则](../src/core/ui.ts#L63)、[设计来源解析](../src/core/ui-design-properties.ts#L138)、[预览字体](../src/renderer/UiComponentVisual.tsx#L31)、[游戏字体生成](../src/runtime/screens.ts#L110)。

**新建议：每项外观都能解释“最终值来自哪里”，并将文本溢出策略独立于字号。**

新机制应先解析每项状态属性的设计来源：默认样式、模板／变体、实例本地；运行时对该属性的参数关联或临时修改继续走已有属性控制。最后按当前交互状态选用相应属性及回退。不要先合成整张状态样式再用一次对象深合并覆盖，否则单独改一个颜色容易抹掉上级字体或其他状态。

可以在属性来源提示中显示“按钮标题 → 实例未覆盖 → 继承标题样式 → 鼠标经过颜色沿用普通颜色”。常态只显示简短来源，完整链在查看详情时出现。恢复某一状态颜色不应顺带清除普通颜色、字体或参数关联。

首版沿用当前状态优先级和回退；“已选中且鼠标经过”“焦点且不可用”等组合规则之后再扩展。内部应预留独立状态标志，而不是未来把所有组合都扩成一个巨大枚举和几十组样式字段。

文本设置建议逐步提供明确策略：

| 策略 | 使用场景 | 必须可见的结果 |
| --- | --- | --- |
| 固定字号，换行 | 菜单说明、剧情摘要 | 文本高度增长；超出范围仍按明确裁切／滚动设置处理 |
| 固定字号，省略 | 存档标题、紧凑导航 | 保留完整内容作提示或详情，不改原文 |
| 缩小以适应 | 必须单行的紧凑按钮 | 显示最小字号与本次有效字号，不能悄悄低于下限 |
| 根据内容调整尺寸 | 标签、按钮模板 | 由约束确定最大宽度；与父布局冲突时可定位原因 |

旧工程继续使用历史规则；切换新策略是显式操作。可先做“有效字号／溢出原因”的检查与长文本预览，再改变排版数据格式，避免再次把旧界面整体排版改掉。

本地化应作为文字内容来源扩展，而不是靠切换一整套控件树完成。当前控件主要保存字符串与系统绑定，导出默认语言为简体中文，尚未具备通用的控件文字资源键契约。未来文字资源键、格式化参数和备用文字要与字号、状态样式独立；同一键翻译变化不得让对象 ID、蓝图引用或模板覆盖失效。已有单向／双向参数控制仍能覆盖该属性，解除后返回原文字来源。

首版值得提供长文本、不同宽高比和较大文字的预览样本。完整翻译管理、复杂语言规则和字体回退链编辑器可后置，但身份模型不能用显示文字作键。

## 5. 多选共同能力编辑比增加更多设置入口更有价值

当前框选可多选，布局工具作用于选中项，但右侧属性明确只编辑最后选中的对象。布局提交已经做到整组预检，父子共同选中时移动根对象，避免重复偏移。这是扩展通用属性批量编辑的现成基础。

代码依据：[右侧属性的多选说明](../src/renderer/UiEditor.tsx#L421)、[选择状态](../src/renderer/useUiSelection.ts#L3)、[父子移动去重](../src/core/ui-arrange.ts#L27)、[原子提交检查](../src/core/ui-arrange.ts#L102)。

**新建议：多选面板显示共同功能能力，区分“值不同”和“来源不同”，操作前形成完整变更计划。**

例如同时选中五段文字与两个带文字的按钮：共同的字体、字号、颜色可以一起改，按钮专属操作不展示为全体共有。不能只按控件 `kind` 相同判断；也不能只看存在同名 `fontSize` 就认定语义相同，列表条目默认字号与整控件文字字号需要明确范围。

多选规则建议如下：

- 多个值不同时显示“多个值”，不显示 0 或末选值来冒充共同值。
- 显示值相同但来源不同，仍标注“来源不同”；用户只改颜色时，不得自动统一字体、解除参数或物化默认值。
- 普通输入表示所有目标设为同一值；增加／减少同一量可另作明确操作，不能从拖动手势猜测用户想要绝对值还是增量。
- 批量改外观针对所有明确选中的对象；父子去重只用于会由父变换自然带动子项的操作，不能把颜色编辑也按根对象去重。
- 先在完整投影状态中检查适用能力、参数限制、模板覆盖容量和来源，再一次提交，一次撤销。任一项不能改时说明具体对象与原因。
- 参数受控项默认不被批量设计值操作隐式写回共享参数。确需只处理可编辑目标时，应是标明数量与排除原因的独立选择；不能静默跳过。
- 恢复默认也须逐目标恢复各自来源，不能把末选项的默认值写到其他对象。

先做字体、颜色、不透明度等明确语义的批量字段。批量删除功能组件、跨模板改结构、批量换输入类型后置，因为它们需要同时处理更多引用与依赖。

响应式布局也应围绕实际编辑收益推进。当前“百分比单位”和缩放预览并不等同于完整响应式系统：布局以项目虚拟分辨率为基准，编辑器窗口变窄通常只是缩放画布。若加入响应式，必须明确触发于游戏视口／安全区／容器尺寸，不能把 Inspector 栏宽当成游戏断点。

建议先覆盖“固定尺寸、拉伸、根据内容调整、最小／最大尺寸、长文字换行”这组常见需求，并提供同一页面的多尺寸预览。宽高比保持、最小尺寸与父空间不够时要有确定优先级。主题变体、设备变体和模板变体不能各自不透明地覆盖同一字段；响应式首版可限定为页面级宽度策略，任意嵌套断点和全套约束求解暂不做。

## 6. 通用扩展的最低标准是预览与游戏遵守同一契约

编辑预览是 TypeScript／浏览器，游戏生成 Ren'Py／Python。属性能力已共享元数据，但布局和输入的执行仍分别实现。当前编译入口先经过项目 schema，构建记录包含项目格式、编译器和 Ren'Py 版本；还没有功能组件插件的依赖版本清单。

代码依据：[属性元数据](../src/core/ui-properties.ts#L9)、[项目解析与编译](../src/runtime/compiler.ts#L94)、[布局双端实现](../src/runtime/ui-layout-runtime.ts#L52)、[构建记录](../src/runtime/service.ts#L120)。

**新建议：先让内置组件遵守版本化能力契约，再开放外部扩展。**

功能定义除字段、图标和编辑器外，应登记：命名空间 ID、数据版本、依赖能力、单／多实例限制、属性与事件版本、预览实现、游戏实现、可迁移版本、引用扫描、释放资源规则。工程记录所用定义版本，构建记录实际解析的能力版本，避免同一工程在两台机器上得到不同默认值和行为。

未知组件或较新版本的数据必须原样保留，显示“此功能暂不可用”及其身份；允许继续编辑其他对象。不要为了打开工程把未知组件转换成普通面板，或保存时清掉字段。游戏导出遇到会影响行为的缺失能力应给可定位的问题，不能预览有效果而导出时悄悄省略。

迁移应是确定的纯数据变换；失败保留原数据和诊断。绘制／预测阶段不能触发事件、创建游戏状态或修改参数。插件的临时资源、动画任务、媒体句柄必须属于具体页面或对象运行实例，在停用、关闭、读档重建时按相同规则释放。

由于两端语言不同，复用一份属性表不足以保证一致。建议为每个功能定义少量中立场景：初始对象数据、按次序的输入／赋值／时间推进、期待的属性与事件。预览和游戏读取同一场景，比较最终状态及事件顺序；布局比较虚拟像素几何，实际文字与效果再做必要的图像验收，允许有明确说明的字形抗锯齿差异。

重点场景应围绕契约：隐藏时取消手势、参数关联时禁止直接写、模板更新后引用仍指向原目标、重复条目重排后输入不串项、停用／读档后不重放进入事件。此处是以后实施时的验收设计，本轮没有新增或运行这些用例。

首版开放声明式的内置功能目录和自定义组合模板已经能覆盖大量扩展需求。任意下载代码、插件市场、热更新及脚本运行环境的复杂度应后置；不能为了“可扩展”先引入一套产品尚不需要的通用脚本平台。

## 下一轮值得交付的最小完整范围

建议在流程连线过渡完成、用户确认组件化实施范围后，选择“图文按钮 + 音量设置行”两类对象做首批。身份／引用、唯一输入和布局责任、逐属性来源与原子修改这四组规则先固定；统一功能卡片、内部对象定位、明确文本溢出、多选共同属性作为作者可见收益。

模板先公开有限字段和事件，版本更新先有明确预览与应用；专用存档列表继续使用原有运行能力，等重复项身份、数据上下文和输入路由明确后再推广。这样可以验证组件体系是否真的减少操作和特殊分支，而非只是增加“添加组件”按钮。

组件研究只保存设计结论，未修改控件产品代码、未启动测试或外部应用，未创建需要清理的临时产物。
