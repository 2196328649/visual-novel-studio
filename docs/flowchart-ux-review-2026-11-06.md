## 2026-11-07 补充：剧情打组与分层导航

### 推荐行为

将「打组」作为本轮流程图整理的核心功能。操作名称建议用「打组为剧情组」，组名称由作者填写，例如「车站支线」「第一章」。整个作品的剧情可以在顶层以一个「游戏内容」容器呈现。

- 顶层显示游戏启动、标题菜单、新游戏准备、「游戏内容」和读取存档。只有点击开始游戏才进入新游戏路径；读档仍直接恢复原有内部节点与台词位置。
- 双击「游戏内容」进入剧情范围，沿用现有章节、小章节导航。此时不重复摆放启动、标题、读档节点，只保留实际跨边界的具名引用。
- 在剧情范围框选若干节点或已有子组，右键「打组为剧情组…」，填写名称，外层收成一张卡片。第一版手工打组范围建议限于同一小章节的同级节点或完整子组；完整作品容器由现有章节结构派生，避免平铺复制所有场景。
- 双击组卡片进入内部，编辑原有台词、选择、条件、参数修改、跳转和演出。组内可继续创建子组。
- 面包屑例如「流程图 / 游戏内容 / 第一章 / 开场 / 车站支线」。点击上级或返回按钮恢复原来的选中节点、缩放和平移位置。
- 卡片显示组名、内部节点数量、入口/出口，以及内部问题数量。不要默认把所有条件、参数和台词摘要塞到卡片上。
- 双击的键盘等价操作是选中后进入；菜单保留「进入剧情组」。允许改名、解组、撤销/重做；解组只展开组织关系，保留内部编辑后的内容和连接。

这里的顶层与内部是同一个流程图工作区的导航层级，不另建「游戏流程 / 剧情流程」两个互不关联的模式。该建议更新了初稿的默认展示：通过进入游戏内容减少全局节点干扰，顶层可直接展示简洁的全局关系。

### 多分支不能压成一个不明含义的继续出口

示例：把车站内的对话、选择、条件和两条支线打成「车站支线」。外层应保留：

```text
上一段剧情 → [车站支线] ─ 一起离开 → 港口
                        └ 留在车站 → 夜晚
```

内部仍是原来的选择与条件。组边界只呈现穿过边界的实际关系：

- **多个入口**：外部若原本能进入组内不同节点，就保留不同的具名入口；多个来源进入同一个内部目标时可以共用该入口。不能把所有外部跳转改到内部第一个节点。
- **多个出口**：不同内部出口及不同后续目标保留可追踪的映射。即使文字相同，也不能仅按显示名称合并；只有连接语义相同且不会失去独立编辑能力时才可简化展示。
- **分支汇合**：原来已经汇合到同一个后续节点的关系可以显示得更简洁，但不能因打组新增汇合、条件判断或自动选择一个分支。
- **未连接出口**：以「未连接」在卡片提示中可见，进入可定位，不自动推测后续剧情。
- **跨组返回与循环**：保留每条原有跳转；不能因为路径穿过组边界而拒绝正常剧情循环或改成执行结束。
- **特殊去向**：返回标题、跳往其他小章节、调用返回分别标明其含义。调用返回的目的地取决于调用处，不能伪造成一个固定的普通继续出口。动态目标明确为运行时决定。
- **内部修改**：在组内新增或删除跨边界连接时同步更新外层入口/出口，保留仍有效端口的身份。外层修改有多种内部来源时先让作者明确改哪条，不批量改接隐藏关系。

### 打组的边界

打组改变组织和显示层级。组内节点、台词、选项的稳定 ID 及原有连接继续作为真实剧情；不要通过删除重建节点来获得分组效果。

- 不把打组自动当作函数调用，不自动建立新的变量作用域或重置参数。
- 不修改原节点的 `sceneId` 或章节归属，不额外触发入场演出。当前运行时在 `vn_current_scene` 改变时执行场景入场动作与场景蓝图，搬到新场景并非单纯整理界面。
- 实际游戏入口仍是原来的 `project.entryId`；若它位于某个组内，外层显示「包含故事入口」和具体位置。对多入口组不能只按卡片位置推断新游戏起点。
- 剧本文本、模块编辑、搜索、诊断、参数使用位置及运行定位仍可到达内部真实节点。已有文本修改应按稳定 ID 保留有效分组归属，并清理被删除节点的归属；只改分组不应重排剧本。
- 分组资料存入工程并支持恢复/撤销，面包屑和视口作为作者视图状态保存。纯文本单独导入到新工程能否携带打组信息，需要明确导出约定，不能默认承诺无元数据仍可恢复分组。
- 编译后的执行路径、调用栈、已访问标记、存档位置和回滚不应因打组发生变化；需要以分组前后对比验证，不能只靠 UI 操作通过判断。
- 「解组」和「删除组及内容」是不同动作，菜单明确命名；删除内容应展示内部节点数量及受影响的外部引用。普通解组保留全部内容及当前连接。
- 编辑器中的剧情组不自动变成玩家剧情回顾地图的可见节点；玩家地图仍按现有显示设置生成。

### 与现有功能的关系

已核对当前源码：

| 现有能力 | 与本次需求的关系 |
| --- | --- |
| `App.tsx` 的「创建可复用段落」 | 新建一个小章节、空段落、返回节点与调用节点，主要是单次调用后回到调用处。没有把当前框选的多分支整体收纳起来。 |
| `model.ts` 的剧情 `call` / `return` | 运行时是真正的调用和返回；普通打组应保留已有行为，不能全部转换成它们。 |
| `story-modules.ts` | 负责模块编辑中的单个剧情段落/独立演出创建、复制和插入，不是多节点层级分组。 |
| 蓝图「封装所选节点」 | 有单入口及单一后续目标等执行边界约束，适合可调用逻辑；不直接适用于任意剧情分支的整理。可借鉴选择与事务交互。 |
| 现有章节、小章节与跨场景返回 | 作为剧情组的归属与导航基础复用，避免新增第二套相互竞争的章节目录。 |

后续若需要同一剧情内容在多处复用，再提供明确的「转为可复用剧情」操作，定义入口、输出结果和调用方式。普通打组默认就是当前内容的组织容器，不让一次内部编辑暗中影响另一份看似独立的剧情。

### 实现与验收建议

先以独立的分组元数据和画布投影实现：组保存名称、成员/父组关系、外层位置及必要的端口显示信息，原剧情节点和执行连接继续为唯一运行依据。完整作品的「游戏内容」根容器尽量由现有结构派生。成员只属于一个直接父组，层级不能互相包含形成循环；剧情自己的循环连接不受影响。

推荐首批包含框选打组、解组、双击进入、面包屑返回、多入口/出口、内部问题提示、搜索/诊断进入、保存恢复与一步撤销。模型一开始支持嵌套，入口不用为每一层再造一种节点类型。把此功能与初稿的视口恢复、跨边界引用、连线标签一起设计。

统一验收时特别覆盖：多入口、多出口、分支汇合、跨组循环、内部含故事入口、调用/返回、内部返回标题、未连接出口；分组前后游戏路径、场景入场次数、参数和稳定 ID 一致；文本/模块编辑后分组仍能定位；取消或失败不留半个组；解组保留分组期间新增和修改的内容；存档读取与回滚不因作者层级改变而错位。

以上为补充设计建议，尚未修改产品源码、增加新工程字段或执行构建与产品验收。本轮无新临时产物。

## 2026-11-07 补充：参考 UE5 蓝图的流程组织

### 可以参考的范围

UE5 的 2D 表现和游戏流程分属不同职责。Paper 2D 提供 Sprite、Flipbook、Tile Map 等二维画面能力；蓝图仍使用通用游戏框架、事件与流程控制。以界面、背景和立绘为主的视觉小说也可以主要使用 UMG，具体显示方案取决于作品。Epic 没有要求所有 2D 作品使用一张统一的总剧情蓝图。

以下视觉小说例子是结合官方机制与本项目需求提出的组织建议，剧情管理器及其节点需由具体项目实现。参考：[Paper 2D 概览](https://dev.epicgames.com/documentation/en-us/unreal-engine/paper-2d-overview-in-unreal-engine)、[Gameplay Framework](https://dev.epicgames.com/documentation/unreal-engine/gameplay-framework-in-unreal-engine)。

### 游戏流程如何组织

| 职责 | UE5 可使用的机制 | 对视觉小说的意义 |
| --- | --- | --- |
| 一次程序运行内跨地图保留的管理状态 | GameInstance，以及按职责组织的管理对象；子系统需按项目能力实现 | 管理当前游戏会话、转场及存读档协调。跨地图保留不等于关闭游戏后自动保存。 |
| 当前地图的规则和初始化 | GameMode；Level Blueprint 处理地图特有事件 | 场景初始化有明确生命周期，普通剧情打组不触发重新加载地图。 |
| 输入、界面创建与交互 | PlayerController、UMG Widget Blueprint | 创建并显示菜单；按钮的 OnClicked 通知对应逻辑。界面显示与剧情推进之间有明确事件。 |
| 对白、分支与演出推进 | 项目自建的剧情管理蓝图／组件，配合结构化剧情资料 | 保存当前剧情位置，展示内容，收到确认、选项或演出完成事件后推进。 |
| 关闭程序后保留的进度 | 自定义 SaveGame | 明确保存剧情位置与必要状态，并在加载后恢复；不会自动保存任意蓝图的执行现场。 |

以事件链理解新游戏和读档，示意如下：

```text
启动事件 → 创建标题界面 → 显示标题界面
点击「新游戏」→ 通知流程管理器 → 初始化本轮进度 → 从故事入口开始
选择并确认存档 → 读取状态 → 恢复对应剧情位置 → 继续游戏
玩家作出选择 → 更新必要参数 → 根据对应分支进入下一段
```

显示标题后，后续流程由实际按钮事件触发。界面用事件分发器或接口通知管理逻辑，可减少按钮直接依赖大量剧情对象的情况。演出与页面在何时完成，需要依据真实完成、关闭、取消或选择事件表达；「开始播放」和「播放结束」是不同时间点。

参考：[创建 Widget](https://dev.epicgames.com/documentation/en-us/unreal-engine/creating-widgets-in-unreal-engine)、[UMG 模板中的按钮事件与事件分发](https://dev.epicgames.com/documentation/en-us/unreal-engine/creating-umg-widget-templates-in-unreal-engine)、[Level Blueprint](https://dev.epicgames.com/documentation/en-us/unreal-engine/level-blueprint-in-unreal-engine)、[保存与加载](https://dev.epicgames.com/documentation/unreal-engine/saving-and-loading-your-game-in-unreal-engine?lang=en-US)。

### 打组最接近 Collapse Nodes

官方的 Collapse Nodes 操作是：框选节点 → 右键折叠 → 得到可命名的 Collapsed Graph 卡片 → 双击进入内部；边界用 Inputs / Outputs 表达，可以展开还原。这与用户本次提出的剧情打组最接近。

| UE5 机制 | 主要用途 | 本项目可以怎样借鉴 |
| --- | --- | --- |
| Comment Box | 给仍在当前画布上的节点加范围和说明 | 提供轻量标注，不改变查看层级。 |
| Collapsed Graph | 将当前一组节点收进可进入的子图，主要用于组织 | 对应剧情组：保留内部真实内容，外层呈现必要的入口和出口，支持双击、嵌套、解组。 |
| Macro | 复用一段节点网络，可提供多个执行入口／出口；编译时展开 | 参考其具名端口与复用交互。涉及复用时须明确共享修改的影响，不能把普通打组默认变成共享资源。 |
| Function | 调用可复用的同步逻辑，带参数和返回值 | 适合条件计算、参数处理等。普通蓝图函数不允许 Delay 等潜伏节点；等待台词、视频或玩家选择的剧情，需采用支持等待的任务与事件模型。 |

折叠仍受所在蓝图图表的规则约束；宏可使用的节点也取决于上下文。不能由上述交互推断任意剧情都能无条件转成函数或宏。本项目的剧情组边界继续按前节的多入口、多出口、跳转、调用返回与稳定 ID 规则设计。

参考：[折叠图](https://dev.epicgames.com/documentation/en-us/unreal-engine/collapsing-graphs-in-unreal-engine)、[Macros](https://dev.epicgames.com/documentation/en-us/unreal-engine/macros-in-unreal-engine)、[蓝图最佳实践](https://dev.epicgames.com/documentation/en-us/unreal-engine/blueprint-best-practices-in-unreal-engine)。

### 对本项目方案的具体修订

1. **同一工作区逐层进入。** 顶层显示启动、菜单与游戏内容；进入后看章节及剧情组；再进入具体段落编辑台词。框选打组沿用 Collapse Nodes 的操作习惯，配合面包屑与视口恢复。层级导航和运行连线分开表达。
2. **出口说明推进原因。** 剧情与游戏步骤根据已有语义显示「继续」「播放结束」「界面关闭」「取消」「选择 A」等出口。条件分支有自己的名称，参数输入保留类型与默认值。执行出口与数据参数的视觉区分，避免把传值误读为播放顺序。
3. **组内也看得清边界。** 双击进入后显示具名入口、出口及外部目标引用，点击可以返回或定位。组内含多个分支或返回标题时，外层仍呈现其必要去向。
4. **内容、界面和演出各自编辑，流程中引用。** 台词继续使用现有模块／文本编辑，页面编辑外观，时间轴编辑演出；流程图中的卡片明确引用对象及推进方式。剧情内页面／演出卡片仍属于前文待讨论的扩展，不能因参考 UE5 就宣称已经支持。
5. **可复用内容单独定义。** 普通打组只整理当前内容。复用需要另外定义参数、结果、等待、调用返回及编辑影响；沿用现有蓝图和可复用段落的能力评估，避免新增重复系统。

大量台词和配置可以借鉴 UE 的 Data Asset／Data Table 思路，以结构化资料保存，再由统一逻辑处理。本项目已经有共享的结构化剧情模型，后续继续让模块、文本和流程图操作这份资料。参考：[Data Assets](https://dev.epicgames.com/documentation/unreal-engine/data-assets-in-unreal-engine?lang=en-US)、[数据驱动玩法](https://dev.epicgames.com/documentation/en-us/unreal-engine/data-driven-gameplay-elements-in-unreal-engine)。

这些建议更新设计依据与交互细节，不要求更换现有 Ren'Py 运行时，也不把 UE 的类名暴露给本项目创作者。本轮仅补充文档，未实施产品改动、编译或产品验收，无新增临时产物。

| --- | --- | --- |
| 全局内容与当前小章节没有明确边界 | `gameFlowCanvasNodes` 在每个场景视图中生成全局节点；画布只有一个场景下拉框 | 切换小章节后仍出现启动和标题，容易误以为它们属于该小章节，或每次都要执行 |
| 默认排列不等于执行顺序 | 默认坐标按步骤库存数组排列；实际运行按 `connections` 的可达路径；插入主要做空位避让 | 接线改序后卡片位置仍可能像旧顺序；跨行、回头线增加。已有「自动布局」，但需要作者主动操作 |
| 线本身缺少明确方向与触发语义 | `SelectableEdge` 使用普通贝塞尔曲线；流程图没有传入终点箭头；完整标签只在单选线时显示 | 跨越整图的线很难顺着读；节点端口的小箭头不能代替远处连线的方向提示 |
| 可编辑性比业务含义更醒目 | 实线代表可改接，虚线代表内置路径 | 作者首先需要知道「自动继续」「点击开始游戏」「返回标题」；能否删除应是附属说明 |
| 返回标题在图上指向游戏启动 | `gameFlowCanvasEdges` 将所有 `end` 的返回线连接到 `flow:launch` | 看起来像重新启动游戏。实际是否重播开场取决于执行策略，图上没有直观表达这层判断 |
| 标题出口并非实际菜单事件总览 | 标题节点固定展示开始游戏、读取存档两个系统出口 | 修改标题按钮或增加按钮事件后，不能把这两条线当作完整的实际菜单行为 |
| 添加页面的默认位置会偏离当前工作 | 添加对话框只支持两个全局阶段；选中剧情节点或连线后打开它，无法继承这些位置，默认回到游戏启动后 | 作者原本想在当前剧情插入页面，却要识别并修改另一套插入位置。当前对话框有位置字段，并非立即无提示写入 |
| 画布暗示可连接的范围过大 | 缺少拖线阶段的目标有效性提示；跨阶段、剧情接标题等主要在松手后报错 | 看起来都是同类端口，实际规则不同，只能反复尝试 |
| 普通拖线可能修改整个游戏的入口 | 新游戏路径接到任意剧情节点时直接修改 `project.entryId`；卡片上没有实际入口徽标 | 作者可能把它理解为增加一条局部连线；原名为「开始」或「流程起点」的节点不一定还是实际入口 |
| 同名节点和共享页面实例难辨 | 真实工程有两个「段落 1」；验收图中同一个页面在两个阶段重复使用，外观相似 | 不易分清这是两份页面还是同一页面的两次使用，修改页面外观的影响范围也不明显 |
| 属性把数个概念同时摊开 | 「等待页面关闭后继续」可以与「计时后自动完成」同时出现，还同时显示底层输入、取消、跳过、数据线说明 | 完成、关闭、取消、等待的关系需要作者自己推断；常用设置淹没在说明中 |
| 搜索与定位割裂 | 搜索主要把未匹配节点透明度降至 0.3，另一个下拉框才负责定位，缺少结果条目 | 小节点仍需肉眼寻找；同名节点难辨；跨小章节内容没有同一个搜索入口 |
| 返回编辑位置缺少连续感 | 画布初始化及切换场景执行适应全图；当前组件没有保存每个场景的视口 | 去界面或蓝图编辑后回来，容易失去刚才的比例和位置。现有跨场景「返回调用处」可以复用，但仅保存来源节点 |
| 跨小章节关系不完整呈现 | 图中只绘制当前场景内的剧情连线；跨场景出口主要靠小外链按钮导航 | 连线看似中断，难以识别来自哪里、到哪里；「调用后返回」与单向跳转也需要更明确 |
| 未接入节点没有直接状态 | 核心层已有「未接入，不会执行」警告；卡片只按 error 标记 invalid | 作者可能以为放在图里就会运行；应把已有诊断变成节点旁可见信息 |
| 小窗口可读性不足 | 1024 宽截图中，固定属性栏及适应全图共同压小节点；控件没有页面溢出，但字仍很小 | 「没有横向滚动条」不能等同于容易阅读 |

## 最初草案：分区、连线与属性

以下第 1 项的默认分区展示已由 2026-11-07 的「游戏内容与剧情组」层级建议更新；节点身份、连线、插入、属性整理与导航连续性的原则仍保留。

### 1. 同一画布，两个有名字的区域

- 上方「全局 · 启动与菜单」，包含游戏启动、开场内容、标题菜单、新游戏准备和读档恢复。
- 下方「当前小章节 · 第一章 / 开场」，包含该小章节的真实剧情节点、分支与跨小章节入口。
- 全局区域默认显示简洁摘要，按需在原地展开。配置了自定义开场时，摘要写明数量及关键内容；未添加内容时显示默认路径。
- 选择诊断、页面使用位置或全局节点时，自动展开对应区域并定位。折叠时仍显示该区域的问题数量。
- 两个区域只是查看方式，不复制运行数据，不新增游戏流程与剧情流程页签。展开/收起不改变连线、执行时机或持久化的作者位置。
- 工作区名称统一为「流程图」，将「蓝图」留给可执行逻辑编辑器；场景选择统一使用现有剧本目录中的「小章节」名称。

概念示例（名称是示意内容）：

```text
全局 · 启动与菜单                                  [展开]
打开游戏 → 开场内容 → 标题菜单
                         ├─ 点击开始游戏 → 新游戏准备 → 故事入口
                         └─ 选择读取存档 → 恢复存档中的位置

当前小章节 · 第一章 / 开场
故事入口 → 车站 → 玩家选择 ─ 留下 → 共同结局 → 返回标题
                         └ 离开 → 第二章 / 港口 ↗
```

返回标题的长线默认收成靠近出口的「返回标题」引用，选中它可以追踪全局路径。执行策略为「每次进入标题」时，详情明确说明会重播开场；其他策略应说明返回时直接显示标题。不能仅改线的目标来掩盖运行语义。

### 2. 连线首先讲清楚运行关系

- 每条执行线有终点箭头。普通顺序线保持简洁；选项、条件、按钮触发、取消和返回等分支持续显示短标签。
- 系统固定连接显示小锁与说明，可选择查看，也能跳到相关界面编辑入口。不要只靠虚线暗示性质。
- 默认路径保持从左到右；跨行回返沿区域外围走线，尽量避让所有卡片。可先保留曲线风格并补方向、路由，避免同时新增多套线型选择。
- 选中节点后突出直接前后关系，其余适度淡化；可主动「追踪路径」。对条件、动态目标显示可能路径，不宣称静态图就是唯一运行结果。
- 「从哪里来 / 接下来到哪里」在右侧提供可点击条目，跨小章节也显示名称。
- 全局区域的默认布局基于实际可达顺序。手动位置继续保留；只在显式「整理布局」时调整作者已有布置，并支持撤销。插入时先显示预期位置，避免添加即重排整图。

### 3. 节点卡片明确身份与影响

- 保留名称和一行有意义的摘要，加短类型标识：剧情、选择、条件、页面、演出、系统、跨小章节。
- 故事入口由 `entryId` 决定，固定显示「故事入口」标识，不能从节点名称推断。
- 页面卡片用动作名称，如「显示：语言选择」，同时显示「关闭后继续」或「2 秒后继续」。右侧显示使用的页面资源与其他使用位置数量，区分「改本次打开方式」和「编辑共享页面」。
- 同名剧情在搜索结果和目标选择中附小章节、台词摘要；不强迫修改已有名称。
- 未接入卡片显示「未接入，不会执行」，警告仍可定位；缺资源、断线和未知目标应有不同说明。
- 跨小章节使用具名引用卡片，如「前往 第二章 / 港口」；调用型关系说明「完成后返回此处」。引用只是导航呈现，不生成新的剧情节点。
- 类型用图标、文字和局部色带表达，核对所有主题；当前主题通用样式会覆盖部分按类型设置的标题颜色。

### 4. 添加与连接跟随作者的意图

- 首选动作是「在这条线中间插入」和「在这个出口后添加」。选择某条线后，插入位置明确显示「A → B」，完成后变成「A → 新节点 → B」。分支节点有多个出口时，让作者先指明出口。
- 在当前图不支持的上下文中，不应默默默认到游戏启动后。近期可先把菜单标明「启动 / 新游戏流程中的页面」，并提供「在当前台词前打开页面」的现有接入入口。
- 拖线时高亮有效目标，并在无效目标旁说明原因；不要等鼠标松开后才解释。目标判断与核心连接校验共用规则。
- 改接新游戏到另一段剧情时，展示「故事入口：旧节点 → 新节点」的具体影响并支持一步撤销；显式「设为故事入口」也可使用同一操作。改变入口属于全局影响，适合在落下连线后用轻量确认明确意图。
- 普通新增剧情节点与现有「创建可复用段落」遵循相同的插入与回退约定；不再采用与当前选择无关的计数网格作为唯一落点。

### 5. 页面属性围绕三个问题组织

首屏只需要回答「显示什么」「什么时候继续」「接下来去哪」。

| 可见设置 | 推荐表达 | 底层处理 |
| --- | --- | --- |
| 页面 | 页面名称 + 编辑页面 + 使用位置 | 保留页面 ID 引用及既有草稿边界 |
| 什么时候继续 | 页面关闭后 / 计时结束后 / 玩家确认后 / 显示后立即继续 | 在视图层组合 `wait` 与 `completion`，不改现有运行规则 |
| 时长 | 仅计时模式显示，使用秒 | 保留原有合法范围 |
| 接下来 | 指向节点的名称，可点击定位或改接 | 与画布连接共用同一操作 |
| 其他行为 | 折叠分组：Esc 取消去向、允许跳过、背景是否可操作、传入参数 | 已修改字段在摘要上有提示；不隐藏重要非默认值 |

「底层输入」可改为「页面显示时，背景是否可操作」，并展示沿用页面设置时的有效值。「页面输入在进入步骤时固定」及数据线说明放到参数区域的帮助中。需要结果分支时提供明确的「编辑结果处理」入口，而不是要求作者自己寻找另一种节点。

完成方式的名称调整不能合并取消、跳过、关闭等运行原因；不同退出路径的行为仍应可查看、可验证。

### 6. 导航与预览连续

- 合并「查找节点或对白」与「定位节点」为一个可定位的搜索结果面板，包含全局节点、各小章节和台词摘要；显示结果数量与当前位置。
- 搜索、诊断、跨小章节跳转自动打开所在区域。跨到界面/蓝图后提供「返回流程图 · 来源节点」，恢复选择、比例与平移位置。
- 按项目与小章节保存视口及折叠状态；来源节点失效时回到小章节并说明，不跳到无关默认节点。
- 平时适应当前区域，显式提供「全图总览」；不为塞下全部系统内容把当前剧情缩成小字。属性栏可折叠，小窗口只在查看属性时占据宽度。
- 现有全局预览明确标为「从启动试玩 / 从标题试玩」；剧情节点显示「从此处试玩」时需说明使用测试初始值，不是自动恢复此前剧情状态。
- 顶层展示「潜在流程」；要显示实际经过哪些节点，需要接现有运行快照/轨迹，不把静态高亮当成真实执行。

## 需要单独讨论的功能扩展

**在剧情的两段之间直接插入页面、视频、演出节点。**

当前全局步骤与剧情节点是两种模型；同一画布不意味着能任意互连。剧情中打开页面已经有能力，但入口会生成调用蓝图并挂在具体台词前，不是一个独立可连接的剧情页面节点。

建议先解决「添加落点不符合当前选择」和现有能力的可发现性。若确认要把页面做成剧情里的独立卡片，再设计其统一表示，覆盖游戏运行、文本/模块双向同步、返回结果分支、撤销与资源引用。

可优先评估把现有页面/演出调用投影为卡片，而不是新增一套只能在流程图运行的页面模型。但投影必须明确对应的原始调用位置；复杂或多个动作无法安全往返时，应保留原调用块，不能丢动作或悄悄拆分台词。

## 实施顺序建议

| 阶段 | 目标 | 主要工作 |
| --- | --- | --- |
| 第一批 | 看得懂、找得回 | 游戏内容容器、框选剧情打组/解组、双击与面包屑、多入口/出口、入口标识、方向箭头与分支标签、跨边界引用、恢复视口、搜索定位、内部问题状态 |
| 第二批 | 操作符合预期 | 线上插入、有效目标提示、入口修改影响、页面属性整理、共享资源使用说明、局部布局与小窗口体验 |
| 后续独立决定 | 更直接地编排复杂流程 | 剧情内页面/视频/演出卡片、页面结果分支、实际运行路径追踪 |

第一批侧重组织、显示与导航，新增分组元数据但保持真实剧情运行依据不变，现已按用户指示实施。第二批其余操作改变和第三批模型／运行时扩展继续单独讨论，不随本轮视觉整理默认开工。

## 若实施后的验收重点

遵循用户要求：全部实施完成后，再统一编译、验证和验收。

1. 无启动配置的旧工程、真实工程只读副本、多个小章节、同名节点、长分支、返回线和断开节点都能辨认；打开/折叠/搜索不改写剧情。
2. 从 A → B 插入节点保持后续连接；多出口插入不会误选出口；无效连接不修改项目；入口变化有明确影响并可一步撤销。
3. 页面资源共享外观、每次使用独立参数的关系表达正确；从页面/演出返回后恢复原节点与视口，处理来源已被删除的情况。
4. 4 种启动策略、新游戏重置、读档恢复、取消/跳过的实际运行行为与图示一致；运行目标未知时仍保留明确的未知说明。
5. 1024 / 1280 / 1920 窗口验证文字可读与实际操作；不只断言 document 无横向溢出。键盘可进入节点、定位搜索结果和使用关键操作。
6. 现有手动坐标不因查看被覆盖；整理布局可撤销；折叠后的连线完整表示跨区关系。连续拖动、缩放和展开较大图后记录交互延迟。
7. 如扩展剧情调用卡片，另验文本/模块/流程图往返、保存重开、运行与返回值，不能用纯前端截图代替。
