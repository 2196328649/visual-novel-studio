## 已确认问题

### 1. [P2] 删除后新建同名段落，会复用旧入口身份

- 位置：`src/core/text-script.ts:552`；引用解析在 `src/core/player-flow-content.ts:34`。
- 触发：把“商店”段落加入自定义图并设置本图名称；从剧本删除它，保存重开；在同一小章节新建名为“商店”、正文不同的段落。
- 实际：生成器仍从小章节、节点种类和名称计算 ID，没有避开自定义图保留的失效引用。旧入口立即恢复有效，把旧本图名称、动作、预设、分组和位置挂到新正文上，不需要点击“修复入口”。重玩旧入口会进入新正文。
- 主线程内存复现包含 JSON 序列化及 `projectSchema.parse`：旧、新 ID 同为 `txt_node_nuxfeg`；删除后缺失入口为 1，新增同名段落后为 0；显示名称仍为“旧入口本图标题”。
- 最小修复方向：为真正新增的段落分配身份时，避开全部已保存自定义图的引用 ID，包括未启用配置、基础方案、覆盖方案和自定义页面；显式携带原 ID 的恢复操作保留其原语义。
- 修复验收：删除→保存重开→新建同名不同正文后，旧入口继续报缺失；只有明确修复才转向新内容。现有文本往返测试主要覆盖改成不同名称，不能覆盖这一情况。

### 2. [P2] 标题含方括号时，重玩确认框可能报错

- 位置：`src/runtime/story-menu-runtime.ts:102`，原始标题传入位置为同文件 `:126`；确认框显示在 `src/runtime/screens.ts:1088`，自定义确认文字的测量和显示在 `src/runtime/ui-widgets.ts:74`、`:89`。
- 触发：游戏进行中，点击一个标题含 `[review_missing_name]` 的可重玩节点，保留默认的跳转确认。跟随剧本和自定义模式均可提供这样的原始标题。
- 实际：`VnFlowEntry` 将原始名称传给 `VnStoryStart`，后者直接拼接 `Confirm` 消息；Ren'Py 默认将方括号内容当作插值表达式，而不是普通名称文字。
- 主线程提取真实 `VnStoryStart` 和本地 SDK 的 `substitutions.parse/interpolate`，内存执行得到 `NameError: name 'review_missing_name' is not defined`。确认消息为 `从「Chapter [review_missing_name]」重新开始？当前未保存的进度将丢失。`。
- 最小修复方向：明确重玩动作接收原始文本还是已转义文本，在一个边界统一处理方括号及花括号。旧默认目录已有 `renpyText` 转义，不能直接不分来源地二次转义。
- 修复验收：普通中文、方括号、花括号、旧默认目录、两种模式、自定义确认框和关闭跳转确认均需覆盖。

### 3. [P2] 合并超过八条成员路线后，已解锁连线可能被隐藏

- 数据裁剪位置：`src/core/story-flow.ts:130`。
- 游戏判断位置：`src/runtime/spatial-ui-widgets.ts:243`；预览同样使用裁剪后的数据，见 `src/renderer/UiFlowPreview.tsx:55`。
- 触发：分组有九个成员，各自连接到同一个组外目标；启用到达进度限制，玩家只到达第九个成员和目标。
- 实际：合并边只保存前八条代表路径，却用它们的端点作为完整的解锁依据。第九条真实连接不参与判断；两端均可进入时，连线仍可能隐藏或变暗。
- 主线程用真实 `playerFlowRuntimeData` 生成数据，再执行产品生成的 `vn_flow_locked`、`vn_flow_edge_alpha`，结果为：组卡已解锁、目标已解锁、连线透明度 `0.0`，保留的来源只有 `source_0` 至 `source_7`，已到达的 `source_8` 被漏掉。
- 最小修复方向：供说明展示的代表路径可以继续限量；另存去重且完整的真实端点对作为解锁依据，预览和游戏遵守同一规则。单纯提高八条的上限仍会留下同类错误。
- 修复验收：超过八个成员的组到节点、组到组；分别覆盖隐藏、变暗、不限制进度，以及只有不相关成员已到达的反例。

### 4. [P2] 缩放、旋转或镜像后，内部节点拖动的距离和方向错误

- 位置：`src/renderer/UiFlowPreview.tsx:74`；完整绘制变换来自 `src/renderer/ui-layout-style.ts:8`，由 `UiComponentVisual.tsx:41` 应用。
- 原因：拖动仅把屏幕位移除以画布缩放和图内缩放，没有应用控件及父级完整矩阵的逆变换。节点和组卡共用此处理函数。
- 主线程用真实 `resolveUiHierarchy`、`uiInverse` 和 `uiTransformVector` 验证：画布和图内均 100%，鼠标向右移动 40 屏幕像素时：

| 控件变换 | 正确的局部位移 | 当前保存的局部位移 | 当前造成的屏幕位移 |
| --- | --- | --- | --- |
| 缩放 2 倍 | 右 20 | 右 40 | 右 80 |
| 旋转 90° | 上 40 | 右 40 | 下 40 |
| 横向镜像 | 左 40 | 右 40 | 左 40 |

- 为排除边界及吸附影响，可将节点先放在 `(300,300)` 并按 Alt 拖动。本轮是实际几何函数与交互源码的内存核对，没有启动桌面模拟鼠标。
- 最小修复方向：从当前绘制几何取得完整矩阵，先逆变换屏幕位移到控件局部空间，再处理画布和图内缩放，复用已有吸附与提交保护。
- 修复验收：自身和父级的缩放、旋转、镜像，节点及组卡，非 100% 画布和图内缩放。

### 5. [P2] 布局计算对条目顺序过于敏感，拖动时反复全量计算

- 排序位置：`src/core/story-flow.ts:146`；拖动触发位置：`src/renderer/UiFlowPreview.tsx:29`、`:35`、`:79`。
- 原因：为每个待排节点反复过滤完整边集合。在逆序线性图中，查找下一节点会多次扫描其余节点和全部边，工作量可随节点数接近立方增长。拖动仅改变坐标，仍重新推导真实剧情连接和完整布局。
- 主线程构建内存线性剧情，预热一次后每种顺序测量三次，未包含 React 渲染或窗口操作：

| 节点数 | 剧情顺序，单次布局毫秒 | 自定义显示列表逆序，单次布局毫秒 |
| --- | --- | --- |
| 100 | 3.56 / 2.14 / 6.49 | 6.03 / 6.01 / 4.79 |
| 300 | 5.88 / 5.84 / 5.82 | 48.90 / 48.67 / 47.64 |
| 600 | 17.06 / 17.28 / 16.95 | 367.12 / 362.38 / 373.75 |

- 这些是合成工程的局部耗时，不能当作真实作品或整页操作的测量，也没有证明此前所有卡顿都来自这里。
- 最小修复方向：建立入边／出边索引，使用就绪节点队列和稳定的循环处理；把剧情连接推导、显示分组投影、几何布局分开。拖动时复用连接关系，只更新相关几何。
- 修复验收：原有分支、合流、循环和布局稳定性保持；顺序／逆序／分组场景进行同环境对比，不用单一耗时阈值代替正确性验证。

## 结构整理建议

1. **分开展示说明与功能依据。** 代表路径是可以省略的说明，解锁端点是不能省略的功能数据。第三项是这种职责混用已经造成的实际错误。
2. **分开剧情关系和界面几何。** `storyFlowLayout` 同时解析入口、遍历路线、合并组、排序和生成坐标；一个位置改动触发所有工作。按这些职责拆开后才能有效复用计算结果，不只是把长函数挪到新文件。
3. **复用坐标转换与手势边界。** 内部流程图与通用控件分别处理拖动，前者没有跟上统一布局矩阵。应共用从屏幕到局部空间的转换及取消规则，保留各自的吸附和写入行为。
4. **统一原始文字的边界约定。** 重玩动作混收原始名称和已转义名称，容易遗漏转义或重复转义。先明确调用契约，再逐个收敛调用来源。

建议先修引用身份和重玩异常，再处理连线正确性、拖动与布局性能；结构整理随对应修复推进，无须一次重写整个编辑器。
